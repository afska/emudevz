# Как можно улучшить твой эмулятор

<div class="embed-image"><img alt="Достижение" src="assets/graphics/achievement_complete.png" style="width: 30%; margin: 16px" /></div>

Поздравляю с таким прогрессом! Теперь эмулятор полностью под твоим контролем, и можно менять всё на своё усмотрение. Есть много способов сделать его лучше. При этом не обязательно отказываться от компонентов, созданных по ходу игры: твой эмулятор уже умеет удивительно много. Пусть он и не самый точный, не недооценивай ни его, ни себя! Многие игры будут работать правильно, если хорошо реализовать мапперы.

Вот несколько улучшений эмуляции, для которых не потребуется серьёзно менять общую архитектуру:

#### 🎮 Контроллер

С текущей реализацией контроллера некоторые игры не реагируют на ввод. В предыдущих главах мы почти не обсуждали понятие `open bus` — открытой шины. Оно означает, что при чтении отдельные биты байта могут содержать мусор или бессмысленные значения: к этим битам ничего не подключено. Вспомни, что при чтении контроллера мы использовали лишь первый бит, бит `0`. Для `99%` игр это подходит, но некоторым нужно видеть значения открытой шины при чтении портов контроллера.

Обычно последним значением на шине оказывается старший байт адреса. Поэтому во многих, хотя и не во всех, случаях именно он используется как значение открытой шины. Контроллер читается по адресам `$4016` и `$4017`, так что здесь это `$40`.

Простой способ учесть это — изменить возвращаемое значение метода `onRead()`:

```js
return 0x40 | +isPressed;
```

После этого игры про `доставку газет`, `сердитого персонажа по имени Макс` и ещё некоторые должны начать принимать ввод!

#### ✋ Прерывания

После прохождения игры можно добавить сколько угодно мапперов NEEES. Но если реализовать IRQ от APU, уточнить момент отправки NMI от PPU или добавить более сложные мапперы со своими IRQ, например `MMC3`, станет заметно, что текущая отправка прерываний в CPU слишком проста и может не справиться со всеми случаями.

##### Запрос, обработка и подтверждение

Обычно BrokenNEEES выполняет инструкцию за `N` циклов, а затем запускает `N * 3` тактов PPU, чтобы тот догнал CPU. Если во время любого из этих тактов возникает NMI, CPU сразу переходит в _обработчик прерывания_. Последний шаг не совсем верен. Настоящий CPU работает примерно так:
```
- Start
- Fetch the next instruction      < <
- Decode instruction               | |
- Execute instruction              | |
- Is there a pending interrupt? --no |
-   |---yes---> Service interrupt ---|
```

То есть PPU, работающий параллельно, лишь _запрашивает_ прерывание. CPU сначала завершает текущую инструкцию и только потом обрабатывает запрос. Устройство может продолжать _запрашивать_ прерывание, пока оно не будет _подтверждено_. Подтверждение означает снятие условия, которое вызвало запрос. Сам переход в _обработчик прерывания_ не обязательно подтверждает его: запрос может оставаться активным до чтения или записи нужного регистра.

##### Возможное решение

IRQ в CPU могут отправлять несколько устройств:

- APU — он может отправлять два разных IRQ!
- маппер — обычно это счётчики циклов CPU или строк развёртки
- сам CPU при выполнении `BRK`

Чтобы обработать все эти источники вместе с NMI и RESET, можно переработать отправку прерываний в классе `Emulator`.

В `Emulator` есть несколько функций `onIntr` внутри `_clockAPU(...)`, `_clockPPU(...)` и других методов. Но они сразу переключают CPU на прерывание, даже если момент неподходящий. Вместо этого функции `onIntr` могут ставить запросы в очередь, чтобы CPU обработал их в подходящий момент с учётом приоритета.

Вот возможные приоритеты от высшего к низшему и компоненты, отвечающие за подтверждение:

| Прерывание              | Кто подтверждает                                          | Приоритет (меньше — выше) |
| ----------------------- | --------------------------------------------------------- | ------------------------ |
| RESET                   | CPU                                                       | `0`                      |
| NMI                     | CPU                                                       | `1`                      |
| BRK (IRQ)               | CPU                                                       | `2`                      |
| Счётчик кадров APU (IRQ) | Регистры APU при обращении CPU                             | `3`                      |
| Завершение DMC APU (IRQ) | Регистры APU при записи CPU                                | `4`                      |
| Маппер (IRQ)            | Маппер при записи CPU в специальный регистр этого маппера   | `5`                      |

<br />

Такой подход позволяет точнее эмулировать IRQ мапперов: игра сообщает мапперу или другому устройству, что прерывание обработано и/или отменено. Иначе на настоящей NEEES устройство продолжает подавать сигнал прерывания. Этот же подход позволит PPU сигнализировать VBlank на цикле `1`, как и задумано, вместо цикла `0`, который мы использовали в предыдущей главе.

Здесь не будет полного пошагового руководства, но можно, например, добавить в CPU псевдорегистр `PendingInterrupts`, который хранит ожидающие прерывания. Для этого подойдёт `InMemoryRegister` или отдельное логическое значение для каждого источника: Reset, NMI, BRK, кадра APU, DMC APU и маппера. Затем добавь простые методы `raise(id)` и `acknowledge(id)`, которые устанавливают и сбрасывают эти значения. В методе `step()` CPU вместо `this._addCycles(operation)` возвращай результат вызова вроде `this._checkInterrupts(cycles)`. Там выбирай готовый запрос с высшим приоритетом. Если такой есть, выполняй прерывание через `this.interrupt(...)` и возвращай параметр `cycles`, скорректировав его, если прерывание было обработано.

Способов хранить и подтверждать ожидающие прерывания много, так что изучай и экспериментируй! В этом примере высшие приоритеты отданы внутренним устройствам.

#### 🖥️ PPU

У PPU тоже много возможностей для улучшения, но подробный разбор далеко выходит за рамки этого небольшого документа. Вот два коротких примера:

- Дополнительные тайлы в `BackgroundRenderer`: PPU настоящей NEEES выбирает больше `32` тайлов на строку развёртки, хотя лишние почти не использует. Некоторые мапперы, например `MMC2` и `MMC4`, следят за этими выборками! Для простоты раньше мы выбирали только `32`. Если добавить неиспользуемые выборки, некоторые игры на `MMC2` и `MMC4` заработают без графических артефактов. В `BackgroundRenderer::renderScanline()` продли цикл до `x < 272`, но рисуй фоновые пиксели только при `x < 256`. Все остальные действия цикла сохрани — больше ничего менять не нужно. После этого в игре про `новичка, мечтающего стать лучшим боксёром`, ринг должен перестать искажаться!

- `SpriteRenderer`: если улучшить PPU для запуска `игры про бокс`, понадобится ещё небольшое изменение отрисовки спрайтов. При особых атаках противник превращается в мешанину искажённых тайлов. Это можно исправить, если метод `_evaluate()` перестанет возвращать список спрайтов в обратном порядке. Но! Тогда появятся проблемы в других играх, например в `третьей игре про водопроводчика`. Ей нужен обратный порядок спрайтов, чтобы враги рисовались за трубами и казалось, будто они поднимаются из них. Чтобы совместить оба случая, можно:
    - Полностью переработать отрисовку спрайтов для большей точности; или:
    - Написать короткий метод, который возвращает `true`, если ID маппера равен `9` или `10`, и по результату выбирать, разворачивать список спрайтов или нет. Учти, это обходной приём, который не соответствует настоящему оборудованию! Так и `третья игра про водопроводчика`, и `игра про бокс` смогут отображаться правильно.

#### 🔊 APU

В некоторых играх, использующих сэмплы DPCM, могут быть слышны искажённый треск и шум. Чтобы исправить это, добавь `this.isActive = false` в метод `stop()` файла `DPCM.js`. Проще всего проверить результат в `игре про бокс`: когда зрители перестают кричать, без этого исправления хорошо слышно жужжание помех.
